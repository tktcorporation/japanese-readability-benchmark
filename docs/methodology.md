# 評価の設計

## 何を測るか

このベンチマークは「LLM が出力した日本語が、想定読者にとってどれだけ読みやすく分かりやすいか」を測る。内容の正確さや情報量は測らない。

評価軸は 2 つある。

| 軸 | 問い | 固定するもの | 変えるもの |
|---|---|---|---|
| A. モデル比較 | どのモデルが素の状態で読みやすい日本語を書くか | 課題、介入（baseline） | モデル |
| B. 介入評価 | ルール・lint・書き直しなどの仕組みで、どれだけ改善するか | 課題、モデル | 介入 |

同じ run の中で両方を回すと、「モデル × 介入」の表として一度に見られる。

## 入力

- **タスク**（`tasks/*.yaml`）: モデルに日本語を書かせるプロンプト。技術解説・リリースノート・障害報告・手順書・メール・要約・FAQ・ADR の 8 種類。想定読者と文字数の目安をプロンプトに含め、出力が比較可能になるようにしている。
- **コーパス**（`corpus/*.md`）: 生成を伴わず「既存の文章をどれだけ改善できるか」を測るための固定文。冗長な規程風、翻訳調、一文が長い報告文など、読みにくい原文を意図的に用意している。すべてこのリポジトリのために書き下ろした架空の文章で、実在の文書ではない。

## 介入（intervention）

介入は `interventions/*.yaml` にステップの列として定義する。

| ステップ | 何をするか | 使うもの |
|---|---|---|
| `generate` | タスクのプロンプトで文章を生成する。`system` を指定するとシステムプロンプトとして渡す。`reuse: baseline` を指定すると生成せず、同じ課題・モデル・サンプル番号の baseline の出力をそのまま使う | モデル |
| `textlint-fix` | textlint の自動修正をかける | `.textlintrc.json` |
| `rewrite` | 指示テンプレートに従って書き直させる。`model` で書き直しモデルを固定できる | モデル |

コーパス起点のときは `generate` を飛ばし、原文から始める。`generate` しかない `baseline` は原文そのものになる。

**後処理だけの介入は baseline の出力を再利用する。** モデルの出力は同じプロンプトでも毎回変わるので、`textlint-fix` や `rewrite-pass` が新しく生成した文章から始めると、生成のばらつきが介入効果に混ざってしまう。`reuse: baseline` を付けた介入は、同じセル（課題 × モデル × サンプル番号）の baseline の文章を入力にする。これで pairwise 比較の差分は介入そのものによるものになる。`bench run` は再利用元の介入を先に実行する。

一方、`style-prompt` のように生成そのものを変える介入は再利用できない。この場合、baseline との差には生成のばらつきも含まれるので、`--samples N` で複数サンプルを取って平均すること。

同梱している介入:

- `baseline`: 素の出力（比較の基準）
- `style-prompt`: 文章ルールをシステムプロンプトで指示（CLAUDE.md や rules に相当）
- `textlint-fix`: 素の出力に textlint --fix
- `rewrite-pass`: 素の出力を同じモデルに書き直させる
- `style-prompt+textlint`: ルール指示 + textlint --fix
- `full-stack`: ルール指示 + 書き直し + textlint --fix（改善の上限の目安）

新しい介入（別のプロンプト、別の lint 設定、スキルやプラグインを模した多段パイプライン）は YAML を 1 つ足せば加わる。

## 指標

### 1. 自動指標（決定的・無料）

`bench score` で計算する。すべて Markdown 記法とコードブロックを除いた本文に対して求める。

| 指標 | 定義 | 向き |
|---|---|---|
| `textlintPer1k` | `.textlintrc.json`（preset-ja-technical-writing）の違反数 / 1000 文字 | 低いほど良い |
| `meanSentenceLength` | 句点で区切った文の平均文字数 | 低いほど良い（目安 40〜60） |
| `longSentenceRatio` | 60 文字を超える文の割合 | 低いほど良い |
| `veryLongSentenceRatio` | 100 文字を超える文の割合 | 低いほど良い |
| `tenPerSentence` | 1 文あたりの読点数 | 低いほど良い（目安 3 以下） |
| `kanjiRatio` | 本文中の漢字の割合 | 低めが読みやすい（目安 0.25〜0.35） |
| `maxKanjiRun` | 漢字の最長連続数 | 低いほど良い |
| `kangoRatio` / `wagoRatio` | 漢語 / 和語の割合（形態素単位） | 漢語が少ないほど易しい |
| `rareruPerSentence` | 「れる・られる」の 1 文あたり出現数（受け身の代理指標） | 低いほど良い |
| `nominalizationPer1k` | 「こと」「という」「を行う」「において」などの迂言表現 / 1000 文字 | 低いほど良い |
| `jreadability` | Lee & Hasebe (2016) の日本語リーダビリティ | 高いほど易しい |

**jReadability** の式:

```
11.724 - 0.056 × 平均文長 - 0.126 × 漢語率(%) - 0.042 × 和語率(%) - 0.145 × 動詞率(%) - 0.044 × 助詞率(%)
```

レベルの目安（日本語学習者向け教材で校正された値）: 6.5〜5.5 初級前半、5.4〜4.5 初級後半、4.4〜3.5 中級前半、3.4〜2.5 中級後半、2.4〜1.5 上級前半、1.4〜0.5 上級後半。ビジネス文書や技術文書は 1〜3 に収まることが多く、一文が極端に長い文章は式の外挿で負の値になる。

本来は UniDic の語種情報を使うが、ここでは kuromoji（IPADIC）を使っているため、語種は「漢字のみ 2 文字以上の名詞・サ変名詞 = 漢語」「カタカナ・英字 = 外来語」「それ以外 = 和語」と近似している。絶対値は本家の実装と少しずれるので、**同じ条件下での相対比較**に使うこと。

textlint は「規則違反」を数えているだけで読みやすさそのものではない。ただし違反密度は人の印象とよく相関する上、`textlint-fix` 介入が何を直したかを追跡できる。

### 2. LLM 判定（`bench judge`）

判定モデル（既定 `claude-opus-5`、`--judge` で変更）に 2 種類の判定をさせる。

- **rubric**: 読みやすさ・分かりやすさ・自然さ・簡潔さ・構成・総合を 1〜5 点で採点。
- **pairwise**: 同じ課題に対する 2 文を比べ、どちらが読みやすいかを A / B / tie で判定。

pairwise のバイアス対策:

- 提示順を入れ替えて 2 回判定し、一致したときだけ勝敗とする。食い違えば tie（位置バイアスの除去）。
- 長さそのものを良し悪しの根拠にしないよう指示する。
- 内容の正確さは判定に含めないよう指示する。

比較の組み方:

- `interventions`: 同じ課題・同じモデル・同じサンプル番号について、各介入 vs baseline
- `models`: baseline について、同じ課題のモデル同士を総当たり

判定は入力テキストのハッシュでキャッシュする（`results/cache/judge/`）。同じ文章を再判定しない。

判定モデルが比較対象の 1 つと同じ場合、自分の出力を好む偏り（self-preference bias）が起こりうる。モデル比較の結論を出すときは、判定モデルを変えて結果が変わらないか確認するか、人手評価と突き合わせること。

### 3. 人手評価（`bench pairs` → `bench serve`）

pairwise と同じペアを Web 画面で人に見せ、「どちらが読みやすいか」を集める。

- 左右はリクエストごとにランダム。内部では A/B で記録する。
- 評価者 ID はブラウザの localStorage に保存した匿名 ID。
- 同じペアに複数の投票があるときは多数決で 1 票に丸めてから集計する。
- `bench report` は人手勝率を LLM 勝率の横に並べ、同じペアがあれば一致率も出す。

## 改善率の定義

介入 X の指標 m について:

```
lower-is-better:  (baseline_m - X_m) / |baseline_m| × 100
higher-is-better: (X_m - baseline_m) / |baseline_m| × 100
```

正なら改善。レポートの括弧内の値がこれ。1〜5 点のルーブリックにも同じ式を使うが、絶対差（`delta`）も report.json に残している。

勝率は `(勝ち + 引き分け / 2) / 比較数`。0.5 が互角。

## 注意点

- **サンプル数**: Claude 4.7 以降は temperature を受け付けないため、ばらつきを見るには `--samples N` で同じセルを複数回生成する。1 サンプルの差は誤差の範囲かもしれない。report.json には標準偏差（`sd`）と件数（`n`）を入れている。
- **プロンプトの固定**: タスクのプロンプトを変えると過去の run と比較できなくなる。変えるときは新しい id にする。
- **判定プロンプトのバージョン**: `src/judge/prompts.ts` の文言を変えたら `*_PROMPT_VERSION` を上げる。キャッシュキーに含まれる。
- **コスト**: rubric はサンプル数 × 1 回、pairwise はペア数 × 2 回の判定を行う。`--limit` で件数を絞って試してから本番を回す。
- **フォールバック**: `fallbacks: true` のモデルは refusal 時に別モデルが応答する。応答した実モデルは `steps[].servedBy` に残るので、モデル比較のときは確認する。
