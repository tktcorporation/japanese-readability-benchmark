=== oauth-explain ===
OAuth 2.0 における認可コードフローというものは、ユーザーが自身のパスワードをクライアントアプリケーションに対して直接渡すことなく、当該アプリケーションに対して限定的な権限を委譲することを可能にするための仕組みであるということができ、その際に登場する役割としては、データの所有者であるユーザー、ユーザーの代理としてデータにアクセスすることを希望するクライアントアプリ、ユーザーの同意を確認したうえでトークンの発行を行う認可サーバー、そして実際のデータを保持しているリソースサーバーの四者が存在しているということになります。

処理の流れに関しては、まずクライアントアプリがユーザーを認可サーバーのログイン画面にリダイレクトさせ、ユーザーがそこでログイン及び同意を行った後に、認可サーバーが認可コードと呼ばれる一時的な文字列を付与した状態でユーザーをクライアントアプリにリダイレクトさせ、クライアントアプリはサーバーサイドにおいて当該認可コードとクライアントシークレットを認可サーバーに送信することによってアクセストークンを取得し、取得されたアクセストークンを用いてリソースサーバーの API を呼び出すということが行われることになるのですが、ここで重要なのは、なぜ認可サーバーがアクセストークンを直接返却しないのかという点であり、それはブラウザを経由するリダイレクトにおいては URL がブラウザの履歴やサーバーのログ等に残存する可能性が存在しており、そこにアクセストークンが含まれていた場合には漏洩時の被害が甚大なものとなってしまうためであって、認可コードであれば一回限りの使用かつ短い有効期限が設定されており、さらにトークンへの交換にはクライアントシークレットが必要とされることから、仮に認可コードが漏洩したとしてもアクセストークンが取得されることはないという安全性が確保されているということが言えます。

=== setup-guide ===
開発環境のセットアップを行うにあたっては、まず Node.js のバージョン 22 以上及び pnpm がインストールされていることが必要となりますので、node --version 及び pnpm --version というコマンドを実行することによってそれぞれのバージョンを確認していただき、インストールされていない場合においてはインストールを行っていただいたうえで、次にリポジトリのクローンを git clone コマンドによって行い、クローンされたディレクトリに移動したのちに pnpm install を実行することによって依存関係のインストールを行っていただくことになります。

その後、.env.example というファイルを .env という名前でコピーしていただき、その中に API キーを設定していただいたうえで、pnpm test を実行していただくことによってテストが実行され、すべてのテストが成功した場合には環境が正しく構築されているということが確認できるということになりますが、なお、pnpm が見つからないというエラーが発生した場合においては npm install -g pnpm を実行することによって pnpm をインストールしていただく必要があり、また、ポート 3000 が既に使用中であるというエラーが発生した場合においては、当該ポートを使用している他のプロセスを停止していただくか、あるいは PORT 環境変数によって別のポート番号を指定していただくことによって対処が可能となっております。

=== faq-answer ===
パスワードをお忘れになりログインすることができないという場合におかれましては、ログイン画面に設置されております「パスワードをお忘れですか？」というリンクをクリックしていただくことによって、ご登録いただいているメールアドレス宛にパスワード再設定用のメールを送信することが可能となっておりますので、当該メールに記載されているリンクから新しいパスワードの設定を行っていただきますようお願いいたしますが、なお、再設定用リンクの有効期限は 30 分となっておりますことにご留意ください。

メールが届かないという場合においては、迷惑メールフォルダに振り分けられている可能性、あるいはご入力いただいたメールアドレスがご登録のものと異なっている可能性が考えられますので、それぞれご確認いただきますようお願いいたしますとともに、それでもなお解決しないという場合におかれましては、サポート窓口（support@example.com）まで、ご登録のメールアドレス及び問題が発生した日時を添えてご連絡いただければ、担当者より対応させていただきます。

=== design-rationale ===
通知配信に関する設計判断についてであるが、現状においては通知配信が同期的な API 呼び出しとして実装されていることに起因して、通知先サービスにおける遅延が API の応答時間に対して直接的に影響を及ぼすという構造となっており、特にピーク時においてはタイムアウトの発生件数が増加しているという状況が観測されていたことから、この問題に対処するための方策として、現状を維持したうえでタイムアウト値を延長するという選択肢、メッセージキューを導入して非同期処理化するという選択肢、及び通知先サービスそのものを内製化するという選択肢の三つが検討されたところである。

検討の結果としては、メッセージキューを導入する選択肢が採用されることとなったが、その理由としては、当該方式によって API の応答時間を通知先サービスの遅延から切り離すことが可能となることに加えて、配信失敗時の再送処理を仕組みとして備えることができるという利点が存在する一方で、内製化の選択肢については必要となる工数が過大であると判断されたためであり、この決定に伴う影響としては、通知の配信が最大で数秒程度遅延することとなる点、及び配信状態を確認するための API を新たに追加することが必要となる点が挙げられる。
